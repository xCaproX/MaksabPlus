# مكسب بلس — فواتير وإيصالات

برنامج بسيط (مرحلة أولى): فواتير مبيعات ومشتريات + إيصالات (تلقائية وحرة)،
مع متابعة مخزون الأصناف وأرصدة العملاء/الموردين والخزن.

- الواجهة: React + Vite + TypeScript، عربي RTL.
- الخلفية: Supabase (Postgres + Auth + RLS).
- العملة: جنيه مصري (ثابتة حاليًا).

---

## قاعدة المنطق

| العملية | تأثير على الحساب | تأثير على المخزون | تأثير على الخزنة |
|---|---|---|---|
| فاتورة مبيعات | الحساب +إجمالي الفاتورة | − كميات السطور | — |
| فاتورة مشتريات | الحساب +إجمالي الفاتورة | + كميات السطور | — |
| مرتجع مبيعات | الحساب −إجمالي المرتجع | + كميات السطور | — |
| مرتجع مشتريات | الحساب −إجمالي المرتجع | − كميات السطور | — |
| إيصال استلام (in) | الحساب −قيمة الإيصال | — | + قيمة الإيصال |
| إيصال صرف (out) | الحساب −قيمة الإيصال | — | − قيمة الإيصال |

- **المسترد في المرتجع يعكس أثره على الرصيد:** مرتجع مبيعات 30 مع مسترد 30 لا
  يغيّر صافي مديونية العميل (المرتجع خصم 30 والمسترد أعادها). المعادلة:
  `الرصيد = (فواتير البيع والشراء − المرتجعات) − (المدفوع − المسترد)`.
  إيصال المسترد يحرّك الخزنة فقط في الاتجاه المعاكس: مرتجع مبيعات ← صرف للعميل،
  مرتجع مشتريات ← استلام من المورد.

- **نوع الحساب مستقل عن نوع الفاتورة:** يمكن البيع لعميل أو لمورد، والشراء من مورد
  أو من عميل. نوع الفاتورة وحده هو ما يحدد حركة المخزون واتجاه إيصالها (بيع ← استلام،
  شراء ← صرف)، ونوع الحساب مجرد تصنيف.
- **التكلفة والربحية:** تكلفة الصنف بمتوسط متحرك لكل صنف ومخزن. تكلفة كل سطر
  فاتورة تُثبت وقت الترحيل، وربح البيع = قيمة السطر − تكلفته، وخسارة الهالك = تكلفته.
  يبدأ المخزون بتكلفة الوحدة التي يدخلها المستخدم، ولا يُسمح بصرف كمية تتجاوز المتاح.
- **الأرصدة الافتتاحية:** رصيد العميل/المورد والخزنة يُضاف إلى الحركات التشغيلية.
  كمية وتكلفة مخزون البداية تُحفظان لكل صنف ومخزن. تصحيح الرصيد بعد بدء الحركات
  يُسجل كتسوية داخلية قابلة للتتبع؛ وتكلفة بداية المخزون تُقفل بعد أول حركة لاحقة.
- **اتجاه الإيصال مستقل عن نوع الحساب:** يمكن الاستلام من عميل أو مورد، والصرف
  لعميل أو مورد. الاتجاه هو ما يحدد حركة الخزنة، ورصيد الحساب ينقص في الحالتين.
- كل فاتورة **مدفوع منها جزء** يولّد إيصالًا تلقائيًا واحدًا بقيمة المدفوع، مربوطًا بها:
  فاتورة البيع ← إيصال استلام، وفاتورة الشراء ← إيصال صرف.
- مدفوع = صفر ← لا إيصال. تعديل المدفوع يعدّل الإيصال، وحذف الفاتورة يحذف الإيصال.
- **الإيصال المرتبط بفاتورة لا يُعدَّل ولا يُحذف مباشرة** (ولا من الواجهة ولا بكتابة
  SQL من العميل)؛ يُدار فقط من داخل الفاتورة. أي محاولة تُرجع
  `receipt_linked_immutable`.
- **الإيصال الحر** (بدون فاتورة) يُضاف ويُعدَّل ويُحذف بحرية من صفحة الإيصالات،
  واتجاهه (استلام/صرف) يُحدَّد من التاب المفتوح عند الإنشاء، ثم يثبت لا يتغير بالتعديل.
- كل شيء يُحسب في Postgres داخل transaction واحدة عبر `create_invoice` /
  `update_invoice` / `delete_invoice` / `create_free_receipt` /
  `update_free_receipt` / `delete_free_receipt`. الواجهة لا تحفظ أي إجمالي.
- الأرصدة (حساب/خزنة/مخزون) **محسوبة** من المستندات، غير مخزّنة، فلا تتعارض أبدًا.

### الحذف والاستعادة

- حذف الفاتورة **حذف سوفت**: تُستثنى هي وإيصالها المرتبط من الأرصدة والتقارير،
  ويُعكس تأثيرها على المخزون، لكن الصف والسطور يبقيان. زر «عرض المحذوفات» في نفس
  الصفحة يعرضها مع زر «استعادة» يُرجع الفاتورة وإيصالها وتأثيرهما كما كانا.
- إيصال الفاتورة المرتبط لا يُحذف ولا يُستعاد من صفحة الإيصالات؛ يتحرك مع فاتورته.
- الإيصال الحر: حذف سوفت واستعادة من صفحة الإيصالات (بنفس الفلتر)، ورقمه لا يتغير.
- الفاتورة المحذوفة لا تُعدَّل حتى تُستعاد (`invoice_deleted`).
- تعديل مدفوع فاتورة إلى صفر يُخفي إيصالها (سوفت) بدل حذفه، وإرجاع المدفوع يُعيد
  نفس الإيصال بنفس الرقم.

### حذف البيانات الأساسية

- حذف حساب/صنف **بدون** أي فواتير أو إيصالات ← حذف نهائي.
- حذف حساب/صنف **عليه** مستندات (حتى المحذوفة سوفت) ← يُعطَّل (موقوف) بدل الحذف،
  مع تنبيه في الواجهة.
- تغيير نوع الحساب **مسموح فقط** إذا لم يكن على الحساب أي فواتير أو إيصالات
  (وإلا يرفضه trigger `accounts_guard_kind`).

### الإيصالات والبيان

- عمود «البيان» (`description`) يكتبه المستخدم في الإيصال الحر (مثل: دفعة تحت الحساب).
- في الإيصال المرتبط تظهر فيه الفاتورة المصدر كما كان في عمود «المصدر» من قبل
  (`فاتورة SAL-000001`).
- «ملاحظات» حقل منفصل ويبقى كما هو.

### تعديل البيانات الأساسية

- الحسابات: تعديل الاسم/الهاتف/الحالة، وحذف/تعطيل.
- الأصناف: تعديل الاسم/الوحدة/الأأسعار/الحالة، وحذف/تعطيل.
- الفواتير والإيصالات الحرة: عرض/تعديل/حذف. تفاصيل الفاتورة تظهر في نافذة منبثقة
  (overlay) بدون مغادرة الصفحة. الإيصال المرتبط يظهر مقفولًا.

## التشغيل

### 1) المتطلبات
- Node.js 18+ (تم التطوير على 22).
- مشروع Supabase.

### 2) تثبيت الحزم

```bash
npm install
```

### 3) إنشاء الجداول في Supabase

20. `supabase/migrations/20261024010000_0020_multi_location_phase_one.sql` (إدارة مواقع المخزون والخزن، واختيار خزنة مدفوع الفاتورة)
21. `supabase/migrations/20261024020000_0021_delete_locations.sql` (تمييز المخزن والخزنة الرئيسيين، وحذف المواقع غير المرتبطة بمستندات)

> البديل لو ثبّتت Supabase CLI: `supabase db push`.

الملف الثالث يُنشئ: شركة واحدة + مخزن «المخزن الرئيسي» + خزنة «الخزنة الرئيسية».

### 4) إنشاء مستخدم الدخول

1. Supabase Dashboard > **Authentication > Users > Add user**
   (إيميل + باسورد، وفعّل «Auto Confirm User»).
2. افتح `supabase/bootstrap_profile.sql`، غيّر الإيميل، وشغّله من SQL Editor.
   هذا يربط المستخدم بالشركة.

### 5) متغيرات البيئة

```bash
copy .env.example .env.local
```

املأ من **Project Settings > API**:

```
VITE_SUPABASE_URL=https://xxxx.supabase.co
VITE_SUPABASE_ANON_KEY=eyJ...
```

### 6) التشغيل

```bash
npm run dev
```

ثم افتح الرابط الظاهر (عادة `http://localhost:5173`) وسجّل الدخول.

## النشر على Vercel

المشروع جاهز للنشر: `vercel.json` فيه rewrites للـSPA، والبناء `npm run build` ينتج `dist`.

1. من [vercel.com](https://vercel.com) → **Add New… → Project → Import Git Repository**.
   (لو الريبو مش ظاهر: **Adjust GitHub App Permissions** وامنح الوصول لريبو `MaksabPlus`.)
2. الإعدادات تُكتشف تلقائيًا (Framework: **Vite**، Build: `npm run build`، Output: `dist`).
3. أضف متغيرات البيئة (Production + Preview + Development):

   ```
   VITE_SUPABASE_URL=https://vnxoliuoxznlwfxalelm.supabase.co
   VITE_SUPABASE_ANON_KEY=<نفس القيمة في .env.local>
   ```

4. **Deploy**. أول نشر بياخد دقيقة تقريبًا.
5. بعد كده أي `git push` على `main` ينشر تلقائيًا (Production)، وأي Pull Request يعمل
   Preview URL — من غير أي خطوة إضافية.

> لو ربطت دومين مخصص، ضيفه في Supabase → **Authentication → URL Configuration**
> كـSite URL. تسجيل الدخول الحالي (إيميل/باسورد) مش محتاج redirect URLs.

## الاختبارات

```bash
npm run test:db
```

يشغّل الـmigrations والاختبارات على Postgres حقيقي (PGlite/WASM) ببيئة مشابهة
لـSupabase (schema `auth`، الأدوار، RLS)، ويُرجع كل شيء في النهاية.

يمكن أيضًا تشغيل ملفات `supabase/tests/*.sql` في Supabase SQL Editor — كلها
داخل transaction وتنتهي بـ`rollback` فلا تترك بيانات.

### ما الذي يُختبر
- حساب إجمالي الفاتورة في قاعدة البيانات (`line_total` / `total`).
- الإيصال التلقائي: يُنشأ، يتعدّل، يُحذف عند مدفوع = 0.
- حركة المخزون: بيع/شراء/تعديل/حذف/نقل بين مخازن، ومتوسط التكلفة المتحرك، ومنع الرصيد السالب.
- أرصدة الحسابات والخزن.
- رفض: مدفوع > الإجمالي، فاتورة بلا سطور، نوع فاتورة غير صحيح، كمية صفر.
- الإيصال الحر: إضافة/تعديل/حذف، والاتجاه (استلام/صرف) مستقل عن نوع الحساب.
- قفل الإيصال المرتبط: يُرفض تعديله/حذفه بالدالة، وكتابة SQL المباشرة لا تجد الصف.
- رفض تغيير نوع حساب عليه مستندات (`account_has_documents`).
- **أي حساب في أي نوع فاتورة:** بيع لعميل أو مورد، وشراء من مورد أو عميل،
  مع بقاء المخزون واتجاه إيصال الفاتورة تابعين لنوع الفاتورة.
- **المرتجعات:** مرتجع مبيعات (SRT) يزيد المخزون ويخصم رصيد الحساب، ومرتجع مشتريات
  (PRT) ينقص المخزون ويخصم رصيد الحساب، والمسترد إيصال معاكس يحرّك الخزنة فقط.
- **الحذف السوفت:** المستند المحذوف يُستثنى من الأرصدة والخزنة، ويُعكس مخزونه،
  والاستعادة تُرجعه كما كان، وإيصال الفاتورة يتحرك معها، ومنع تعديل فاتورة محذوفة.
- **حذف البيانات الأساسية:** حذف نهائي بلا مستندات، وتعطيل فقط عند وجود مستندات
  (حتى المحذوفة سوفت).
- **اتجاه الإيصال:** استلام/صرف مستقل عن نوع الحساب، وحركة الخزنة حسب الاتجاه،
  وترقيم منفصل RCP/PAY، وإيصال الفاتورة يتبع نوعها.
- **عزل الشركات:** مستخدم شركة أ لا يرى ولا يعدّل ولا يحذف بيانات شركة ب
  (RLS)، ولا يستخدم حسابات/خزائن شركة أخرى.
- **التكلفة والهالك:** متوسط التكلفة عند الشراء والصرف، تثبيت تكلفة السطر، ربح البيع
  وخسارة الهالك، رفض الصرف فوق المتاح، وعدم إنشاء إيصال أو تغيير رصيد الحساب للهالك.
- **الأرصدة الافتتاحية:** أرصدة موقعة للحسابات، رصيد الخزنة، كمية وتكلفة المخزون لكل
  مخزن، التصحيح بعد الحركات كسجل جديد، وقفل تكلفة البداية بعد حركة مخزون لاحقة.
- **مصالحة المخزون:** إذا كان رصيد المخزون صفرًا رغم وجود صافي فواتير موجبة، يُعاد
  بناؤه من الفواتير النشطة. تعديل كمية شراء يطبق فرق الكمية دون طرح السطر القديم مؤقتًا.

## ترقيم المستندات

`RCP-000001` (إيصالات استلام), `PAY-000001` (إيصالات صرف).
